# edu-llm: a local AI practice tutor for students

A self-hosted backend that lets students practise programming, databases and related disciplines on the
university's local network. A student logs in, picks a discipline and a topic, and gets a task. The system can
give **graduated hints**, but **never solves the task for the student**. Everything runs on-premises on a CPU-only
virtual machine (Hyper-V) with a local LLM served by [llama.cpp](https://github.com/ggml-org/llama.cpp). No data
leaves the campus.

> **Status:** in developmnt backend only (REST API). There is no web frontend in this repository for a while.

## Features

- **Local LLM on CPU.** llama.cpp `llama-server` (OpenAI-compatible API) in Docker, no GPU required.
- **Authentication by student ID (INS) and password.** Passwords are generated by an administrator; students
  cannot change them. Argon2 hashing, JWT sessions, login rate limiting.
- **Two practice modes.**
  - *Topic practice*: the student chooses a discipline and a topic and receives either an existing task from the
    bank or a newly generated one.
  - *General practice*: the system selects tasks the student handles worst (long solving time, unsolved, many
    hints, many wrong answers) using a weakness score per topic and per task.
- **Tasks by identifier.** If a request mentions a task code (`T-000123`), the task is always returned from the
  database; the LLM is never asked to invent it. This is enforced in code, not in the prompt.
- **Three-level hints, no solutions.** Level 1: which concept to recall. Level 2: where to start. Level 3: a plan
  without calculations. Generic hints are cached per task; custom questions go through the LLM with RAG context and
  a post-filter that blocks leakage of the reference answer.
- **Answer checking.** `exact`, `numeric` and `choice` answers are checked by code. Free-text answers use an LLM
  judge whose comments pass the same leakage filter.
- **Statistics.** Per student, discipline and topic: tasks attempted/solved/total, hints requested, time spent.
- **RAG knowledge base.** Markdown lecture material is chunked, embedded and stored in PostgreSQL (pgvector).
- **Task bank workflow.** Tasks live as YAML files in git, are validated and imported idempotently; AI-generated
  tasks go through a teacher review queue.

## Architecture

```
Student --> HTTPS --> Caddy (TLS, reverse proxy)
                      └-> FastAPI (auth, task logic, statistics)
                            ├-> PostgreSQL 16 + pgvector (users, tasks, attempts, knowledge base, vectors)
                            ├-> llama-server "chat"   (Qwen2.5-7B-Instruct, Q4_K_M, CPU)
                            └-> llama-server "embed"  (bge-m3, 1024-dim embeddings, CPU)
```

Design points that matter on a CPU-only host:

- Concurrency is capped by a semaphore matching llama-server slots (`-np`), with a bounded waiting queue;
  when full, the API answers `503` with `Retry-After`.
- Tasks mostly come from the bank rather than being generated on the fly; hints for levels 1-3 are cached.
- RAG context is short (2-3 chunks) and the system prompt is constant.
- Vector search is exact (no ANN index) and always filtered by topic or discipline, which is fast at this scale.

## Quick start

### 1. Virtual machine

Create a Generation 2 Hyper-V VM (Ubuntu Server 24.04) with static memory (24 GB recommended), up to 16 vCPUs
(not more than the physical cores), a fixed-size VHDX and an External virtual switch. Disable processor
compatibility mode so that AVX2/AVX-512 stay visible to llama.cpp. Give the VM a static IP and add a DNS A-record
for the service name.

### 2. Models

```bash
pip install -U "huggingface_hub[cli]"
huggingface-cli download Qwen/Qwen2.5-7B-Instruct-GGUF --include "*q4_k_m*" --local-dir models
# plus a bge-m3 GGUF (1024 dimensions) in models/ ; file names must match docker-compose.yml
```

### 3. Configuration

Create `.env` (never commit it):

```ini
POSTGRES_DB=edu
POSTGRES_USER=edu
POSTGRES_PASSWORD=<long random string>
DATABASE_URL=postgresql://edu:<password>@db:5432/edu
JWT_SECRET=<64+ random characters>
ADMIN_PASSWORD=<initial administrator password>
LLM_URL=http://llm-chat:8080
EMBED_URL=http://llm-embed:8080
```

### 4. Run

```bash
docker compose up -d --build
docker compose logs -f llm-chat      # wait for the model to load
```

### 5. Initial data

Apply migrations that are not yet part of `db/init.sql`:

```bash
for f in db/migrations/*.sql; do docker compose exec -T db psql -U edu edu < "$f"; done
```

Create disciplines and topics (see `kb/topics.txt`), then log in as `ADMIN` and create students:

```bash
TOKEN=$(curl -sk https://<host>/api/auth/login -H 'Content-Type: application/json' \
  -d '{"ins":"ADMIN","password":"..."}' | jq -r .access_token)

curl -sk https://<host>/api/admin/students/bulk -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '[{"ins":"2024-0001","full_name":"Ivanov I.","group_name":"IT-21"}]'   # passwords are returned once
```

> **Host name.** Underscores are not valid in host names (RFC 1123) and the `.local` suffix is reserved for mDNS.
> Prefer a name such as `my.edu-org.local` or a name in a real internal DNS zone. Distribute the Caddy root
> certificate (`/data/caddy/pki/authorities/local/root.crt`) to client machines.

## API overview

All routes are served under `/api/v1`.

| Method and path | Role | Purpose |
|---|---|---|
| `POST /auth/login` | any | Log in with INS and password, returns a JWT |
| `GET /disciplines`, `GET /disciplines/{id}/topics` | student | Catalog |
| `POST /tasks/request` | student | Get a task (topic / generated / general mode, or by task code) |
| `GET /tasks/{code}` | student | Open a task by its code |
| `POST /tasks/{code}/hint` | student | Next hint level, optionally with a question |
| `POST /tasks/{code}/submit` | student | Submit an answer |
| `GET /me/stats` | student | Own statistics |
| `GET /admin/stats` | admin | Statistics by student / discipline / topic |
| `POST /admin/students/bulk`, `POST /admin/students/{ins}/reset-password` | admin | Create students, reset passwords |
| `POST /admin/tasks` | admin | Create or update a task by `external_id` (duplicate detection) |
| `GET /admin/tasks` | admin | Task bank with solve statistics (review queue: `?status=draft`) |
| `POST /admin/tasks/generate` | admin | Batch generation of draft tasks (run when idle) |
| `PATCH /admin/tasks/{code}/status` | admin | Approve or reject a task |
| `POST /admin/kb/ingest` | admin | Add or replace a knowledge-base document |

## Content workflows

### Knowledge base (`kb/`)

One Markdown file holds one document type (`theory`, `pitfall`, `example`, `glossary`) with a YAML header:

```markdown
---
discipline: APR
topic: "Recursion"
doc_type: theory
title: "Recursion: basic concepts"
source: "Lecture 7"
author: "Author Name"
---
## What a base case is
...one idea per `##` section, 300-1200 characters, self-contained...
```

```bash
python3 kb/check_kb.py kb/APR/recursion/*.md       # validate locally
python3 kb/ingest.py "$TOKEN"                      # upload; same title = replace
```

Each `##` section becomes one chunk with an embedding. Never put solutions of bank tasks into the knowledge base:
hint generation retrieves `theory`, `example` and `pitfall` chunks and could leak them.

## Hint and answer safety

- Task lookup by code is a regular expression and a database query executed before any LLM call.
- Reference answers and solutions are never returned by student-facing endpoints.
- Hint text is checked against the reference answer and solution lines; on a leak, the request is retried with a
  stricter prompt and then replaced by a neutral fallback hint.
- Answers of type `exact`, `numeric` and `choice` are compared by code; the LLM judge is used only for free text.
- Hint level is derived from the number of hint requests on the attempt, not from the client.

## Weakness score (general practice)

For every attempt: unsolved (with activity) = 1; solved = 0.4 · time over the expected time + 0.4 · hints / 3 +
0.2 · wrong answers / 3 (each term capped at 1). A topic's weakness is the smoothed mean `(Σw + 1) / (n + 2)`;
a topic is drawn with probability proportional to weakness², and inside it the weakest task is chosen.

## Database

`db/init.sql` creates the base schema; later changes are numbered files in `db/migrations/`.  
Main tables: `users`, `disciplines`, `topics`, `tasks`, `task_hints`, `attempts`, `submissions`, `hint_requests`, `kb_documents`, `kb_chunks`; views `v_attempt_weakness` and `v_student_topic_stats`.

## Operations

- **Backups:** `pg_dump` on a schedule plus the git repositories (`kb/`, `bank/`) which are the sources of truth
  for content.
- **Monitoring:** CPU load and latency of `/v1/chat/completions`. If a typical hint takes longer than about
  40 seconds, use a smaller model or rely more on cached hints.
- **Tuning llama.cpp:** `-t` should not exceed physical cores; `-np` of 4-6 slots is usually the limit on CPU.
- **Network:** only Caddy publishes ports (80/443); PostgreSQL and llama-server are reachable only inside the
  Docker network.

## Security notes

- Students cannot change their passwords; there is no such endpoint.
- Access tokens expire after 8 hours; login attempts are rate limited per INS.
